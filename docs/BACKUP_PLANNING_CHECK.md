# Live backup planning check

The cPanel Backup Planning Check workflow runs on manual dispatch and when its own files are merged to main. It uses the already authorized SSH/staging secrets and never deploys the application. It validates an independent empty staging database first, then reads ONLY live database metadata in a READ ONLY transaction and filesystem metadata under the known Laravel root. It does not read user rows or file contents, print filenames, publish DB credentials, create backups, lock tables, write production records, change .env, restore data or run migrations.

Reports table/engine counts and visible view/trigger/routine/event counts. These metadata views are privilege-limited: zero visible objects does not prove absence. External/broken symlinks and non-InnoDB tables explicitly stop automatic continuation. File metadata excludes root .git/vendor/node_modules and does not traverse symlinks. A complete production document-root/volume/upload mapping is still required: this inventory cannot establish whether separate application/public roots contain additional assets. Parent free bytes are an estimate, not a backup space reservation.

The source configuration is read from Laravel's config cache if present or parsed .env and process environment, without booting Laravel. Source credentials are used for read-only metadata only; staging credentials remain separate. Configuration URL ambiguity, unreadable files and connection errors fail with generic messages that suppress sensitive values. No private backup or SQL dump enters GitHub artifacts.

A passing report only allows designing the correct backup method. It is NOT backup/restore proof, APP_KEY escrow, off-host retention, a source-write cutover plan, staging acceptance or production release authorization. Before restoring into staging, obtain a complete consistent current database and file backup, retain the original key securely, verify off-host copies and file/record integrity, then restore only into a separate private root and verified empty staging DB. No overwrite of live or nonempty staging is authorized by this workflow.
