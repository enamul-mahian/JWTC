# Private current production backup

The owner requested current database/uploads backup and staging restoration as part of production readiness. This workflow creates a NEW unique private backup directory; it never edits source records, live configuration, source uploaded files or nonempty staging. It requires empty independent staging, 100% InnoDB live tables, no known source symlinks, and cPanel-verified document roots. The selected domain public root must be within the selected app root. Backup/key directories must be outside ALL cPanel document roots and the source root, with 0700 directories and umask 0077. Unknown/external root mappings, source changes and command errors abort.

Outputs under $HOME/jwtc-private-backups/<backup-id>: database.sql.enc, application-files.tar.gz.enc and manifest.json. The random encryption passphrase and exact active original APP_KEY are retained separately under $HOME/jwtc-backup-keys/<backup-id>.key and <backup-id>.app-key. Never print these keys, add to Git or put backup/key files in a public folder. No private data is uploaded to Actions artifacts. SQL credentials are used only from existing live configuration in memory and the dump subprocess's environment, never command-line password arguments.

SQL uses single-transaction/quick export with routines, triggers, events and hex blobs; command failure never falls back to an incomplete dump. File archive includes current app source/.env/uploads with exclusions: .git, vendor, node_modules, storage/framework, storage/logs and bootstrap/cache. Full source file hashes are compared before/after export/archive so changing files cause failure. SQL and file archives are encrypted using AES-256-CBC + PBKDF2 (200000 iterations, random salt); each archive is decrypted to a private temporary file and plaintext SHA-256 compared before removing plaintext originals. The private manifest records encrypted/plaintext hashes, source file aggregate/count and original APP_KEY fingerprint. Encrypted archives are NOT authenticated-encryption containers; retain the manifest securely and verify both encrypted and decrypted hashes before any later restore.

Concurrent source-schema DDL is not coordinated; do not run unrelated migrations/DDL during backup. The database snapshot and filesystem hashes do not constitute a full application-wide coordinated freeze, offsite retention or restore proof. Source writes to excluded runtime logs/sessions may continue. Source credentials' metadata visibility can hide objects; zero visible routines/events is not proof of absence. The mysqldump full-object export may fail if grants are insufficient, in which case there is no successful backup manifest. Partial private outputs may remain on failure for review and are not certified backups. Do not delete any source or earlier successful backup.

The workflow runs manually or when its own files are merged to main, using already configured CPANEL_* and staging Secrets. It writes only private NEW backup/key outputs on the hosting account. Successful local backup does NOT authorize production deployment: independently retain an off-host encrypted backup and keys via separate secure handling, restore SQL into the empty staging schema and files into a new nonpublic root, compare stable IDs/file references and hashes, preserve original keys/SEO/analytics, and complete staging migrations/browser/API/SMTP acceptance before cutover. No restore, migration, application update or deployment is performed by this workflow.
